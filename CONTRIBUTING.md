# Contributing to Redoubt

Thank you for your interest in contributing to Redoubt!

Contributions of all kinds are welcome, including bug fixes, new features, security improvements, documentation, and suggestions.

This document describes how to contribute to the project.

## 1. Getting Started

Before contributing, make sure you have:

- Git installed.
- Python 3.12.
- A working development environment.
- Basic familiarity with Python and Git.

### Clone the repository

```bash
git clone https://github.com/FreyFlyy/Redoubt.git
cd Redoubt
```

### Set up a virtual environment

```bash
python -m venv .venv
```

Activate it:

**Linux:**
```bash
source .venv/bin/activate
```

**Windows (PowerShell):**
```powershell
& ".\.venv\Scripts\Activate.ps1"
```

### Install dependencies

```bash
python -m pip install -r requirements.txt
```

## 2. Making Changes

Before implementing significant changes, consider opening an issue to discuss your proposal.

This helps avoid duplicated work and ensures that proposed changes align with the project's direction.

You are welcome to work on:

- Bug fixes.
- New features.
- Performance improvements.
- Security improvements.
- Documentation.
- Tests and test coverage.

Keep changes focused and avoid introducing unrelated modifications.

## 3. Testing

All contributions involving code must be tested before submission.

Run the complete test suite from the repository root:

```bash
PYTHONPATH=. python -m pytest -v -ra tests/
```

Pull requests must not introduce unexpected test failures, errors, or regressions.

New functionality should include appropriate tests whenever applicable.

## 4. Pull Requests

All code contributions must be submitted through GitHub Pull Requests.

1. Fork the repository.
2. Create a dedicated branch for your changes.
3. Implement and test your changes.
4. Commit your changes with descriptive commit messages.
5. Push your branch to your fork.
6. Open a Pull Request targeting the `main` branch.

Pull Requests should include:

- A clear description of the changes.
- The reason for the changes.
- Relevant issue references, if applicable.
- Testing performed.
- Screenshots or additional information when relevant.

Keep Pull Requests focused, reasonably sized, and easy to review.

## 5. Code Review and Maintainer Decisions

All contributions are subject to review.

The project maintainer has final authority over:

- Whether a contribution is accepted or rejected.
- Whether requested changes are necessary.
- The implementation and architectural direction of the project.
- The project's priorities and roadmap.
- When and how changes are integrated.

Submitting a Pull Request does not guarantee its acceptance.

The maintainer may request modifications, suggest alternative implementations, close Pull Requests, or decline contributions that do not align with the project's requirements or direction.

Final decisions regarding the project remain with the maintainer.

## 5.1. AI Contributions

Contributions may be written by humans, generated by AI tools, or produced through a combination of both.

The origin of a contribution is not relevant to its eligibility for review or acceptance.

Regardless of how a contribution is produced, the **individual submitting it is fully responsible for its content**, including:

- Code correctness and functionality.
- Security implications and potential vulnerabilities.
- Compliance with applicable licenses and third-party rights.
- Accuracy of documentation and claims.
- Testing, validation, and overall quality.

Submitting AI-generated code does not transfer responsibility to the AI tool or its provider.

Contributors are expected to understand, review, and take responsibility for everything they submit, regardless of its origin.

The same review and acceptance criteria apply to all contributions.

## 6. Security

Security vulnerabilities **must not** be disclosed through public GitHub issues or Pull Requests before being responsibly reported.

Please follow the instructions in [SECURITY.md](SECURITY.md) when reporting security vulnerabilities.

## 7. Development and Release Policy

Contributors are not expected to manage releases or publish distribution artifacts.

Versioning, release procedures, and release requirements are maintained separately by the project maintainer.

See [RELEASE_WORKFLOW.md](RELEASE_WORKFLOW.md) for further information.

## 8. Final Notes

Contributions are appreciated, but maintaining Redoubt's security, reliability, and architectural consistency takes priority over the quantity of contributions.

Thank you for helping improve Redoubt!
